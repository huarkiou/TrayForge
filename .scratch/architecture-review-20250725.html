1. Collapse the ViewModel adapter layer

Strong in-process adapter
viewmodels/dashboard_viewmodel.dart viewmodels/process_viewmodel.dart viewmodels/tray_viewmodel.dart viewmodels/settings_viewmodel.dart

Before: 4 shallow adapters

Screens (Dashboard, Settings, ProcessDetail)
DashboardViewModel -- just rebuilds list
ProcessViewModel -- mirrors state + output
TrayViewModel -- colour + menu proxies
SettingsViewModel -- list CRUD + save passthrough
ProcessManager + ConfigStore

After: deep ProcessManager

Screens

ProcessManager (deepened)

state + output streams, process list, tray colour,

mutation methods, config save orchestration

ConfigStore (persistence only)

Problem

Four ViewModels are thin adapters whose interface nearly matches their implementation. Each subscribes to ProcessManager streams, mirrors state, and rebroadcasts via ChangeNotifier. The deletion test: remove any one and the screen code that replaces it would be about the same size.

Solution

Deepen ProcessManager with the aggregation logic currently split across ViewModels -- process list ordering, tray colour computation, config mutation orchestration -- and have Screens listen directly. ProcessManager already exposes output streams and state streams; adding a processListStream and trayColorStream would collapse 4 adapters into 0.

Wins

  • Locality: state + output + colour + list logic in one module
  • Delete 4 shallow adapters (~500 lines)
  • Interface: same number of streams, fewer classes to learn
  • Tests hit one seam: ProcessManager, not N ViewModels

2. models.dart leaks Flutter into the foundation

Worth exploring in-process
foundation/models.dart

Before: UI import in foundation

foundation/models.dart

import 'package:flutter/material.dart';

ProcStateX.statusColor => Colors.green/red/grey

Every file that imports models.dart pulls in Flutter

After: colour mapping at the seam

foundation/models.dart

ProcState -- enum only. No Flutter import.

Screens / Widgets map ProcState to Color at the UI seam

Problem

ProcStateX.statusColor returns Color from package:flutter/material.dart, so every module importing models.dart transitively depends on Flutter. The foundation cannot be used in a pure Dart context -- no CLI, no server, no backend tests without the full Flutter SDK.

Solution

Remove the statusColor getter from the extension. Define a simple status-to-colour mapping at each call site, or extract a single helper at the widget layer. The logic is a 3-case switch -- not worth coupling the foundation to the UI framework for.

Wins

  • Foundation becomes framework-free -- testable with pure Dart
  • Seam between domain types and UI presentation is explicit
  • Deletion: remove models.dart -- no Flutter dependency follows it

3. Config save loop: reentrant save-reload-rebuild

Strong in-process
viewmodels/settings_viewmodel.dart services/config_store.dart services/process_manager.dart main.dart 
flowchart TD

    CC -->|3| TV["TrayViewModel.onConfigChanged"]
    SV -->|4| PMR["ProcessManager.reloadConfig"]
    PMR -->|5 start/stop| PM["ProcessManager._procs"]
    PM -->|6 state stream| DV
    PM -->|6 state stream| TV
    classDef leak stroke:#dc2626,stroke-width:2px
    class CC leak

Problem

SettingsViewModel._save() calls both ConfigStore.save() (which broadcasts configChanged, triggering _reload() on the same SettingsViewModel) and ProcessManager.reloadConfig(). The broadcast stream couples every ViewModel to every save, producing implicit reentrancy that's almost impossible to reason about when debugging.

Solution

Split configChanged into directed notifications. ConfigStore.save() persists only; callers that need to react call ProcessManager.reloadConfig() explicitly. The save flow becomes: save, then reload if needed, then Views poll. No broadcast fan-out, no implicit loop.

Wins

  • Locality: one save path, no broadcast side effects
  • Interface shrinks: configChanged stream can go
  • Tests: no need to mock broadcast stream timing

4. OutputPipeline: interface = implementation

Worth exploring in-process
foundation/output_pipeline.dart services/process_manager.dart

Before: two stateless helpers

After: deep output module

OutputPipeline (deepened)

- strip ANSI & detect WebUI

- buffer lines, trim to history limit

- periodic flush timer

- expose Stream<String>

ProcessManager (shrinks by ~60 lines)

Problem

OutputPipeline is exactly as complex as its implementation: two pure static functions. Meanwhile, the output buffering, history-limit trimming, and periodic-flush-timer logic lives inside ProcessManager private methods. The module boundary is in the wrong place.

Solution

Deepen OutputPipeline into a proper buffered output module. Accept a raw line stream, strip ANSI, detect WebUI URLs, buffer to a configurable limit, and expose a clean Stream. ProcessManager _onOutputLine, _startFlushTimer, and buffer management move behind the OutputPipeline interface.

Wins

  • Locality: all output logic tested through one module
  • Interface grows from 0 (static) to 1 meaningful class
  • Leverage: N process instances share one output pipeline design
  • ProcessManager.settle() no longer needs flushNow workaround

5. ProcessManager constructor: side-effect storm

Worth exploring in-process
services/process_manager.dart test/services/process_manager_test.dart

Before: implicit side effects on construction

ProcessManager(...)
_cleanupStalePidFiles() -- PID scan + kill
_autostartAll() -- launches processes
Tests need settle() to wait

After: explicit init

ProcessManager(...)
no side effects
pm.init() -- explicit
cleanupStalePidFiles()
autostartAll()

Problem

ProcessManager constructor fires stale PID cleanup and autostart as side effects. Tests compensate with settle() -- a complex async coordination mechanism (completers, pending counters) that exists only because the constructor does too much. The interface leaks: callers must know about hidden async work happening in the background.

Solution

Make the constructor side-effect-free. Expose a single Future<void> init() method. Callers become explicit about when cleanup and autostart happen. settle() and its completer machinery can be deleted -- tests await init() directly.

Wins

  • Interface clarifies: construction vs. activation are separate steps
  • Delete ~30 lines of settle / completer / pending-count machinery
  • Tests: await pm.init() instead of await pm.settle()
  • No hidden async work -- callers control timing

6. RealProcessRunner.findPidsByCwd: infinite recursion

Bug in-process
services/process_runner.dart foundation/process_cwd.dart 
// process_runner.dart
import 'package:trayforge/foundation/process_cwd.dart'; // exports findPidsByCwd()

class RealProcessRunner implements IProcessRunner {
  @override
  Future<Set<int>> findPidsByCwd(String cwd) async {
    return findPidsByCwd(cwd);  // calls itself, not the top-level import
  }
}

Problem

The instance method findPidsByCwd shadows the same-named top-level function imported from foundation/process_cwd.dart. The call inside the method body resolves to itself -- infinite recursion. The cleanup_cwd feature cannot work through RealProcessRunner.

Solution

Either alias the import (import '...process_cwd.dart' as cwd; and call cwd.findPidsByCwd(cwd)), or rename the method to avoid shadowing.

Why no test caught this

Tests use MockProcessRunner which has its own pidsByCwd field -- the real RealProcessRunner code path is never exercised. This is a seam that exists only as a hypothetical -- the mock adapter is the only one tested.

Top recommendation

#1 -- Collapse the ViewModel adapter layer

This is the highest-leverage deepening. Four shallow adapters -- collectively ~500 lines -- exist solely to relay streams and rebroadcast state. The deletion test passes cleanly for all four: remove them, and ProcessManager gains the aggregation they currently scatter. It is also the highest-recent-touch area: the last 10 commits touch Dashboard, Settings, and their ViewModels repeatedly. Start here, and candidates #2 (models.dart Flutter leak) and #3 (config save loop) become easier to address because you are working with fewer modules.
